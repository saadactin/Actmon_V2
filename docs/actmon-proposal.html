Section 01

Executive Summary

ActMon is a vendor-neutral, self-hosted AI monitoring platform that unifies deep database observability, infrastructure health, and multi-cloud discovery — giving database-driven enterprises a single pane of glass and an embedded AI DBA copilot across their entire data estate.

What Is ActMon

ActMon is an operations-intelligence layer that connects to the database engines, servers, and cloud accounts an organization already runs. Rather than deploying one tool per engine — one for SQL Server, another for PostgreSQL, a third for MongoDB — ActMon collects deep, engine-native telemetry from MySQL/MariaDB, PostgreSQL, Microsoft SQL Server, Oracle, MongoDB, and ClickHouse, correlates it with host-level metrics from Linux and Windows servers (via lightweight agents or agentless SSH), overlays AWS, Azure, and OCI cloud inventory and cost, and applies AI to turn all of it into grounded, actionable answers.

Why It Was Created

Database teams typically operate 4–8 disconnected monitoring tools — engine-specific consoles, OS utilities, cloud dashboards, and hand-rolled scripts. DBAs spend their day logging into individual servers, running ad-hoc health-check queries, and assembling status reports by hand, while commercial per-instance-licensed suites price out mid-market estates. ActMon was conceived to close this gap: one installable platform, every engine, agent or agentless, with AI assistance built in from day one — not bolted on.

Vision

To become the default operational-intelligence layer for database-driven organizations worldwide — a platform where every database, server, and cloud account, regardless of vendor, can be seen, understood, and acted on from one console in real time.

Mission

To eliminate monitoring silos and manual DBA toil by delivering vendor-neutral deep-dive monitoring, intelligent alerting, and AI-assisted diagnosis and remediation that database teams can trust and act on with confidence.

Business Value

ActMon targets four categories of business value: operational (15-second telemetry, correlated alerts, AI-run diagnostics that shorten time-to-root-cause), financial (illustrative consolidation of per-engine tool licenses and reduction of manual DBA reporting hours), strategic (a durable, self-hosted data layer that survives engine migrations and cloud moves, with full data sovereignty), and cultural (a shared, trusted source of truth across DBA, infrastructure, DevOps, security, and leadership teams).

Long-Term Strategy

ActMon's roadmap began with unified multi-engine monitoring and deep-dive dashboards, then layered in the AI copilot, AI alert triage, and self-healing automation. The platform now progresses toward machine-learning anomaly detection, capacity forecasting, broader engine and Kubernetes coverage, and enterprise integrations — evolving from a monitoring console into a proactive operations partner embedded in daily database administration, while remaining fully self-hosted and vendor-neutral.

Section 02

Industry Challenges

Database and IT operations teams face a consistent set of structural problems that stem from decades of engine-specific, point-solution tooling rather than unified platform design.

Tool Sprawl

Each engine ships its own console — SSMS, pgAdmin, OEM, Compass — plus separate OS, cloud, and alerting tools, each with its own login and data model.

No Central Monitoring

No single view shows database health, host resources, replication state, backups, and cloud posture together in real time.

Manual Health Checks

Daily DBA checklists, morning health reports, and management summaries are assembled by hand from scripts and screenshots.

Alert Noise

Threshold storms and duplicated alerts from multiple tools bury the one signal that matters, causing alert fatigue and missed incidents.

Reactive Firefighting

Slow queries, lock storms, and replication lag are discovered after users complain — not before impact.

Slow Root-Cause Analysis

Was it the query, the index, the disk, or the VM? Cross-domain evidence lives in different tools owned by different teams.

Per-Instance License Cost

Commercial database-monitoring suites price per monitored instance, making full-estate coverage unaffordable for growing organizations.

DBA Skill Shortage

Senior multi-engine DBAs are scarce; junior staff lack the tribal knowledge to diagnose engine-specific incidents quickly.

Backup Uncertainty

Backups run from cron jobs and maintenance plans with no central verification of success, schedule drift, or PITR readiness.

Cloud Blind Spots

Cloud resources, spend, and security posture live in provider consoles that database and infra teams rarely open.

Compliance & Audit Load

Access reviews, login trails, and change evidence must be compiled from scattered logs for every audit cycle.

Data-Sovereignty Constraints

SaaS-only observability platforms require shipping telemetry off-premises — unacceptable for BFSI, government, and regulated industries.

The Common Root Cause

Each of the challenges above is a symptom of the same underlying condition: operational truth about the data estate is fragmented across more tools than any team can watch. Every additional engine, server, or cloud account adds another console rather than removing one. Without a vendor-neutral intelligence layer, this fragmentation compounds year over year — and the cost of "finding out what is happening" grows faster than the cost of running the databases themselves.

Section 03

Market Opportunity

Database observability is moving from a DBA convenience to a board-level reliability and cost concern, creating a structural window for a vendor-neutral, AI-native, self-hosted platform.

Data-Estate Sprawl & Polyglot Persistence

Modern applications no longer run on one database. A typical mid-size enterprise operates relational engines for transactions, MongoDB for documents, ClickHouse for analytics, and managed cloud databases alongside on-premises estates. Every new engine multiplies the monitoring surface — and the pool of DBAs fluent in all of them is shrinking, not growing.

AI-Assisted Operations & Copilots

Generative AI is transforming how operations teams interact with telemetry: natural-language questions over live metrics, AI-suggested diagnostics, and automated report generation are lowering the skill barrier for day-to-day database operations. Platforms with AI embedded in the core workflow — not offered as an add-on SKU — are positioned to capture this shift.

Market Driver — Tool Consolidation

Budget owners are actively cutting overlapping monitoring subscriptions; a single multi-engine platform is a direct consolidation play.

Market Driver — DBA Shortage

Experienced multi-engine DBAs are retiring or moving to cloud vendors; AI copilots help junior teams operate at senior level.

Market Driver — Data Sovereignty

Regulated industries and public sector increasingly require self-hosted observability with no telemetry leaving their network.

Future Trends Shaping the Category

  • Self-hosted, vendor-neutral platforms that consolidate per-engine tools without shipping data to a SaaS.
  • AI copilots embedded in daily workflows — health questions, incident triage, SQL generation, report drafting.
  • Autonomous remediation progressing from advisory suggestions to supervised self-healing actions.
  • Unified database + infrastructure + cloud views replacing separate DBA, sysadmin, and FinOps consoles.
  • Predictable licensing displacing per-instance pricing that penalizes estate growth.

Business Opportunity for ActMon

ActMon sits at the intersection of these trends: a self-hosted, AI-native platform covering the six most-operated database engines plus infrastructure and cloud, installable in minutes on a single Ubuntu server, and multi-tenant by design — which additionally opens the managed-service-provider (MSP) market, where one ActMon deployment can serve many client organizations with isolated data and role-based access.

Problems With This Model

Time Lag

Detection depends on user complaints; diagnosis depends on someone logging in. Impact accumulates the whole time.

Tribal Knowledge

Diagnosis lives in the heads of senior DBAs and in unversioned scripts — unavailable at 3 a.m. or after attrition.

No Correlation

Query, lock, host, and cloud evidence are viewed in isolation, hiding cross-domain root causes and fueling blame cycles.

Effort Overhead

Skilled engineers spend a meaningful share of their time collecting and formatting data rather than fixing systems.

Layer-by-Layer Explanation

Databases & Hosts

Engine-native views (performance_schema, pg_stat_statements, DMVs, V$ views, profiler, system tables) plus host CPU, memory, disk, network, processes, and services.

Collectors

A dependency-light host agent enrolled via one-time token (Windows MSI, Debian DEB, RHEL RPM, or shell script), or agentless SSH collection for hosts where agents aren't permitted. Both feed identical dashboards.

Ingest & Processing

Agents push every ~15 seconds; server-side collectors pull on the same cadence. Each sample is classified by kind (infra or database), technology, and connection before storage.

Metrics Pipeline

A three-tier store: PostgreSQL for durable metadata, Redis for the hot last-hour ring buffer powering live dashboards, ClickHouse for long-range history and the searchable logs hub.

AI Engine

The copilot answers questions grounded in live metrics; the alert agent chooses and runs the next diagnostic command; error analysis explains engine errors; self-heal executes supervised fixes.

Dashboards, Alerts, Reports, Actions

Role-scoped dashboards refresh in near real time; alert rules evaluate continuously; scheduled reports email themselves; and remediation happens in-platform via terminal, backup, and self-heal modules.

Architectural Principles

  • Agent or agentless by choice — every host can be monitored via the lightweight agent or via SSH; both paths share the same collector logic and produce identical dashboards.
  • Read-oriented, non-invasive integration — engine telemetry is gathered from native statistics views; remediation actions are explicit, permissioned, and audited.
  • Vendor neutrality — no engine or cloud is privileged; connectors use native drivers and provider APIs rather than proprietary middleware.
  • Multi-tenant by design — every table carries an organization scope, enforced by a tenant context on every request.
  • AI above a normalized layer — models consume the unified pipeline, so AI capabilities improve without re-architecting collection.

Core Modules

ActMon's five core modules form the platform's primary value proposition, each addressing a distinct, high-frequency pain point identified across database-driven organizations.

ActMon AI CopilotConversational AI

Purpose: Give every role a natural-language interface into the live data estate — ask a question, get a grounded answer with real numbers.

Key Features
  • Streaming chat grounded in live dashboard data — health questions are answered from real-time metrics, not model memory
  • Per-dialect SQL generation, EXPLAIN and performance analysis, error diagnosis, index and schema advice
  • Organization-scoped context: the copilot knows which connections exist and their environments
  • One-click report downloads (connections, health summary, slow queries) generated from live statistics
  • In-app navigation commands — ask for a page and the copilot takes you there
Business Need

Junior engineers don't know which of six engines' system views holds an answer, or how to query it. The copilot removes that lookup burden and encodes senior-DBA judgment.

Business Benefit

Reduces time spent searching for information and lowers the skill barrier for operating a polyglot estate.

Workflow
  • User asks a question in plain language
  • The engine detects intent, resolves the target connection, and injects live metric data
  • The response streams back with actual figures and suggested next steps
  • User drills into the underlying dashboard or downloads a report
Future Enhancements

Pluggable local LLM for air-gapped sites; proactive copilot suggestions triggered by detected anomalies.

Unified Multi-Engine MonitoringDeep Visibility

Purpose: Provide engine-native deep-dive dashboards for six database technologies from one console — not lowest-common-denominator graphs.

Key Features
  • MySQL/MariaDB: performance, queries, tables, locks, Galera/replication, users, storage, backup & PITR, logs
  • PostgreSQL: performance, pg_stat_statements queries, locks, replication, storage, backup & PITR, config
  • SQL Server: DMV-based performance, Always On, storage, backup, users, locks
  • Oracle: sessions, SQL, tablespaces, Data Guard, redo logs, sys stats, parameters, live queries
  • MongoDB: operations, profiler, collections, oplog, sharding, transactions, WiredTiger
  • ClickHouse: query log, partitions, merges, replicas, clusters, system metrics
Business Need

Multi-engine estates have no single screen showing overall status; this module is the foundation every other module builds on.

Business Benefit

Removes the need to switch between vendor consoles — and removes per-engine tool licenses along with them.

Workflow
  • Connection or agent registers an engine
  • Collectors ingest engine-native statistics every ~15 seconds
  • The pipeline classifies and stores samples; dashboards render per-engine tabs
Future Enhancements

Additional engines (Redis, Elasticsearch, Cassandra) and managed-cloud database flavors.

Smart Alerts & AI TriageIncident Intelligence

Purpose: Turn raw thresholds into actionable incidents — and let AI run the first diagnostic steps before a human even opens a terminal.

Key Features
  • Alert rules with live evaluation and an active-alerts board with acknowledgement
  • Drill context — every alert resolves to its live database connection for immediate investigation
  • AI diagnostics agent — the AI decides and runs the next diagnostic command, step by step
  • AI analysis — one click produces an explanation and suggested fixes for the alert
  • SMTP integration for email notification and report delivery
Business Need

Operators buried under threshold noise need the path from "alert fired" to "root cause identified" compressed to minutes.

Business Benefit

Shortens the path from alarm to root cause and reduces cognitive load during incidents.

Workflow
  • Rule evaluates against live pipeline data and fires
  • DBA opens the alert; drill context connects to the affected database
  • The AI agent proposes and executes diagnostic steps; findings accumulate on the alert
  • DBA applies the suggested fix or escalates with full evidence attached
Future Enhancements

Escalation policies, on-call schedules, and Slack/Teams/webhook channels (see companion roadmap document).

Slow Query & Index IntelligencePerformance Engineering

Purpose: Surface the specific queries and missing indexes costing the most, per engine, with drill-down detail and AI explanation.

Key Features
  • Slow-query digests from engine-native sources (performance_schema, pg_stat_statements, DMVs, V$SQL, profiler, query_log)
  • Query detail drill-downs with EXPLAIN plans (MySQL/PostgreSQL/MSSQL) and Oracle live queries
  • Index analysis per engine — unused, missing, and duplicate index candidates
  • Error log collection with AI error analysis that explains and prioritizes engine errors
Business Need

"The database is slow" is the most common, most expensive ticket in IT — and the evidence to fix it is scattered across engine internals most teams never query.

Business Benefit

Converts vague performance complaints into a ranked, fixable work list — often deferring hardware spend.

Workflow
  • Collectors sample statement statistics continuously
  • Digests rank by total time, calls, and rows examined
  • DBA drills into a digest, views the plan, and requests AI explanation or index suggestions
Future Enhancements

Plan-change tracking and visual plan diff; workload comparison between time windows.

Self-Heal & AutomationAutonomous Operations

Purpose: Move beyond observing problems to fixing them — with supervised, audited automation.

Key Features
  • MySQL Self-Heal terminal — guided auto-remediation with a persistent history log of every action taken
  • Scheduled backups with point-in-time recovery management for MySQL, PostgreSQL, and SQL Server
  • Scheduled email reports per engine, generated and delivered automatically
  • Background schedulers: agent collector, agent reaper, backup jobs, report jobs, resource collector
Business Need

Routine remediation — restarting replication, clearing runaway sessions, verifying backups — consumes DBA hours and invites human error at 3 a.m.

Business Benefit

Shifts recurring toil from people to supervised automation, with every action logged for audit.

Workflow
  • A known failure pattern is detected or selected
  • The self-heal flow proposes the remediation and executes on approval
  • The action and outcome are written to the self-heal history
Future Enhancements

Self-heal playbooks extended to all six engines; anomaly-triggered supervised remediation.

Section 13

Database Architecture

ActMon uses a polyglot persistence approach — matching each data workload to the storage engine best suited to its access pattern, in a hot/warm/cold tiering model.

PostgreSQL — Durable Metadata

Connections, agents, organizations, users, RBAC policy, alert rules, backup and report schedules, and snapshots — structured, transactional data where strong consistency matters.

Redis — Hot Tier

The latest sample and a one-hour ring buffer per metric stream, indexed for instant live-dashboard reads at 15-second resolution. Degrades gracefully to a no-op if unavailable.

ClickHouse — History & Logs

Per-technology time-series tables for long-range history and aggregation, plus the platform's searchable logs store — optimized for fast scans over large date ranges.

Stable-Facts Deduplication

Slow-changing facts (versions, configurations, topology) are deduplicated in PostgreSQL rather than re-written every cycle, keeping storage lean while preserving change history.

Why This Combination

No single engine efficiently serves 15-second live reads, durable transactional metadata, and multi-month history scans at once. By separating these workloads — Redis for "now," PostgreSQL for "what is configured," ClickHouse for "what happened" — ActMon scales each tier independently while keeping every engine tuned to its strength. Status transitions additionally use hysteresis (error streaks and offline grace windows) so dashboards report state changes confidently rather than flapping.

Security Architecture

ActMon follows a defense-in-depth model appropriate for platforms that hold credentials to production databases — where integrity and least privilege matter as much as confidentiality.

Authentication

Centralized login with JWT session tokens and OTP verification at sign-in; bcrypt password hashing throughout.

Authorization & RBAC

Role-based access mapped to a page-level permission matrix — each role sees exactly the modules and pages it is granted.

Multi-Tenant Isolation

Every record carries an organization scope enforced by tenant context on every request — tenants cannot see each other's estates.

Secrets Handling

Installer-generated database password and JWT secret written to a root-owned environment file with 600 permissions; nothing hard-coded.

Audit Logs

Audit trail, login history, active session tracking, and password history for traceability and compliance evidence.

Agent Enrollment Security

Agents enroll with one-time install tokens; database credentials for agent-side tests never leave the monitored host.

Transport Security

nginx front end ready for TLS termination; API and websocket traffic proxied on the private interface.

Backup & Recovery

Scheduled, centrally tracked backups with PITR support protect both monitored databases and the platform's own stores.

Least-Privilege Collection

Engine telemetry reads from native statistics views; remediation is a separate, explicit, permissioned path.
